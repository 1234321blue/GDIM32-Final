### Group Devlog
Our project uses raycasting to implement the item interaction system. The main feature that requires this is our pickup mechanic, where the player can press E to collect an object they are looking at. In our TryPickup() method, we create a Ray using new Ray(playerCamera.position, playerCamera.forward). This uses the camera’s forward direction vector to project a line into the world, and we call Physics.Raycast(ray, out hit, interactRange) to detect objects in that direction within a certain distance. The math behind this works because the ray uses a normalized direction vector to calculate positions along a line in 3D space like shown in the demo in class. If the ray intersects with a collider tagged "item", we store the object in the heldItem variable and attach it to the holdPoint. Raycasting is relevant in our project because it allows us to detect what the player is looking at using direction vectors instead of relying on trigger zones which makes the interaction system more precise and scalable. This use of vector direction and spatial detection is important to how our first-person interaction system works/functions.

## Final Submission
### Group Devlog
The three design patterns we used in our project was a finite state machine, a Singleton pattern, and inheritance and polymorphism. We utilized the finite state machine in the NPC class of our code, having it represent what mood the NPC was in. Based on this, once the method EndGame() was called, depending on what mood the player was in, happy, mad, or pillow (don't think too hard about that one), the EndGame() method would SetActive one of the three ending screens. This was beneficial for us as it allowed us to define mutually exclusive endings for our game, setting clear different paths based on the NPC's state. For the Singleton pattern, we created a Locator class that held the singular NPC class and Player class we had in the scene, which we utilized a lot through our Item class and it's child classes, mostly referencing the NPC class for replacing the startingDialogue variable that held what dialogue route the NPC would start with the Item class's uniqueDialogue variable. Overall, this allowed us to decouple our code and make our messy code just a little bit cleaner. Finally, we utilized inheritance and polymorphism, as mentioned earlier, in our Item class and its child classes, DistractionItems and Milk. The Item class held the basics for allowing every item to interact with the NPC (by destroying itself on collision) and giving the NPC new dialogue to start with the player. The child classes would than inherit these attributes, but than have their specific item types lead towards different endings. The DistractionItems class would lead to the frustrated NPC ending, so it would tell the NPC class how many times items of its type interacted with the NPC, and once it hit a certain number, the ending would trigger in the NPC class. The Milk class would tell the NPC whether or not the milk was given to the NPC, and once it did, it would trigger the given milk ending in the NPC class. Overall, this allowed for us to implement specific and different actions for items that also shared a few actions, resulting in less repeated code and code that was instead more condensed.
